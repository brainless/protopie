# Epic 003: MVP live preview integration

Crates: `protopie-api` (wire contract), `protopie-server` (project preview processes), `protopie-gui` (project and chat UI), `protopie-ui-agent` (generator fixes found during browser testing)
Related: [Epic 001](001-deterministic-modify-parser.md) (project model, modify/answer, review/apply and recovery), [Epic 002](002-parser-unit-test-driven-development.md) (parser)
Status: T1–T4 and T7 complete; T5–T6 investigations and browser follow-ups remain open; T8 automation and documentation are locally verified, with CI and the remaining macOS browser release checks pending. Analysis and scope recorded below.

## Goal and baseline

Make a template-derived project usable through the GUI: select or create a project, launch its Vite server, apply a chat edit, and see the result in the system browser through Vite's reload behavior. Run the generated output in a browser for the first time and fix defects exposed by that run.

The existing code already creates named projects from `reference/`, initializes `.protopie/model.json`, skips `node_modules` when copying, lists projects, and provides a GUI project dropdown and New Project modal. Project chat already uses `/projects/modify` and `/projects/answer` with a persistent conversation ID, previews diffs, and applies a plan against its revision and plan ID. The backend already journals source, manifest, session and retry-ledger changes, detects external edits, and supports interrupted-apply recovery. Reuse these paths.

The MVP keeps **preview then Apply** as the edit policy. A live preview begins immediately after Apply; auto-apply and persistent undo are separate product work. This preserves the review behavior delivered by Epic 001 while the generated application and Vite behavior are first validated. Editing must also work when the preview server is stopped.

Out of scope: Deno, installing Node for the user, deployment/export, an embedded browser, remote or multi-user preview, a new parser vocabulary, undo, migration of projects missing required template regions, and Windows/Linux manual verification. Keep process and path handling portable where practical; macOS is the manual release target.

## Architecture and decisions

```text
GUI ──HTTP──> protopie-server ──> ui-agent modify/answer/apply ──> project files
                         │                                       │
                         └──> PreviewManager ──> npm ci, Vite ───┘
                                      │               │
                             status and log tail   HTTP + HMR
                                      │               │
                                      ▼               ▼
                                     GUI       system browser
```

- The server checks `node`/`npm`, installs project dependencies, owns project child processes, and returns status and a loopback URL. The GUI continues to own its existing server process and opens the URL with the platform browser opener; it does not run project tooling.
- For this single-window MVP, the server manages **one active project preview**. Launching a different project stops and reaps the previous preview before starting the next. A repeated launch for the active project returns its current status. Canonical project paths are the manager's identity; launch validates that the directory is a supported template-derived project before installing or starting anything.
- Install state is separate from the agent's manifest and journal. A successful `npm ci` records a fingerprint of both `package.json` and `package-lock.json`; launch reinstalls when either fingerprint changes or `node_modules` is absent. A failed or cancelled install records no successful stamp. New projects do not copy `node_modules`.
- Start the project's installed Vite directly through the checked Node executable, bound to `127.0.0.1` with a strict, selected port. The manager owns cancellation, process-group termination, reaping, and bounded logs for both install and Vite. Readiness requires a successful HTTP response **and** a live child; the status reports the URL actually used. A stale or occupied port must cause a bounded retry or a clear failure, never a URL for an unrelated process.
- The journal provides recoverable application across files, not one atomic filesystem snapshot for Vite. T6 measures whether Vite observes temporary intermediate states and decides if mitigation is needed. Do not change the journal protocol based on an assumed HMR problem.

## Tasks and acceptance criteria

### T1: Runtime check and preview wire contract (P0)

Add shared API types and an on-demand server endpoint reporting the located Node and npm executables, their versions, and a structured unavailable/unsupported reason with an actionable message. `reference/package.json` has no `engines` field; its locked Vite 8.3.2 and Solid Vite plugin require Node `^20.19.0 || >=22.12.0`. Use that explicit template minimum, update it when the lockfile changes, and show the actual required range in errors. Record the npm version; installation itself confirms that npm can consume the lockfile. Resolve and run the same Node/npm executables during launch that the check reported.

Define launch, stop, restart, status and cursor-based log-tail request/response types. Status distinguishes `Stopped`, `Preparing`, `Starting`, `Running { url }`, and `Failed { reason }`; include enough project identity and operation generation for the GUI to discard stale polling responses. Environment failures are structured responses, including missing executable, bad version and command failure, rather than generic strings.

Done when API serialization tests and server tests with injected executable lookup/command output cover missing tools, a too-old Node, valid versions and command failures without depending on the host environment.

### T2: Preview manager and lifecycle (P0)

Implement the manager and endpoints in `protopie-server`. Launch validates the project model and required regions, checks the runtime, runs `npm ci` when required, starts local Vite, and returns a status while preparation continues. Expose bounded, ordered stdout/stderr lines with a cursor so polling returns only new lines. Report install errors, Vite early exits and readiness timeouts with the relevant log tail.

Serialize launch/stop/restart/switch requests so an in-flight install or start cannot create a second preview or survive Stop. Stop terminates the install or Vite process group, waits for it, and returns `Stopped`; restart performs Stop then Launch. Detect an unexpected child exit and move to `Failed`. On normal server shutdown, including the existing GUI stdin-close path, clean up children before exit. Document hard-kill behavior; a later launch must not mistake an orphan or a stale port for its own server.

Done when fake-process tests cover successful install/start, install failure, readiness timeout, early exit, repeated launch, stop during install/start/run, project switch, occupied port and log cursor bounds. A separate ignored real-process test creates a fresh project, performs its first `npm ci`, fetches its Vite URL, stops it, and verifies the child has exited. The CI generated-build job runs this test and fails if its Node prerequisites are missing.

### T3: Project entry and eligibility (P0)

Turn the existing dropdown/New Project flow into a clear entry view with **New Project** and **Continue**. Reuse `init_named`, `slugify`, `/projects`, and the current GUI conversation; add last-modified display from the project's model file timestamp. Preserve collision handling and invalid-name errors. A newly created project should be selected and ready for chat and launch without another initialization step.

List older or unsupported project folders with an unavailable state and the existing actionable unsupported-project explanation. Block Launch for them before `npm ci`; do not migrate them in this epic. Keep the existing rule that the template copy excludes `node_modules`.

Done when server/GUI tests cover create, list, name collision, invalid name, selecting an existing project, and unsupported-project launch. A fresh project can still complete the Epic 001 preview-and-Apply path.

### T4: GUI preview controls (P0)

Add Launch, Stop, Restart and Open in browser controls to the selected-project view. Render environment errors, preparation/start progress, the running URL, failures and a collapsible log tail. Poll status and logs while work is in flight and while running, stop polling on project switch or window closure, and ignore replies for a previous project or operation generation. Open the browser once after a user-initiated launch reaches `Running`; keep Open in browser for later use. Do not open it merely because a poll discovers an already-running preview.

Done when pure GUI state tests cover control visibility, transitions, polling, stale responses, and error/log display. Manually run the GUI on macOS and record whether launch opens the project URL.

### T5: First browser run of generated output (P0, investigation)

Create a fresh project and exercise the supported operation families through the GUI: navigation, labelled items and each destination choice (new page, existing page, external URL, unlinked); pages/routes; image, form, footer, button and hero changes; supported styling and positioning; and the `Share the <label> across pages` clarification flow. Use the exact supported prompts and answer options from Epics 001/002; create prerequisites before style or context commands.

For each scenario, inspect the rendered result, browser console, Vite overlay, and Vite logs. For routing, click links, load a route directly, and use back/forward. Check CSS modules, Solid 2 context/provider behavior and Solid Router in the running app. Record the prompt/answers, expected result, observed result and evidence in the investigation log. Fix reproducible generator/template defects with a regression test where automation can capture the failure. Record design questions as follow-ups instead of silently changing command semantics.

Done when each operation family has a browser result or a named follow-up, and every landed fix passes its regression and generated-project build checks.

### T6: Reload during multi-file apply (P1, investigation)

Observe Vite while applying changes to several files, especially page creation/route registration and context creation/provider/consumer updates. Record transient overlays, stale routes/modules, full reloads versus HMR, and elapsed time from Apply completion to visible change. Run the same prompts more than once and note whether behavior is repeatable. Measure first-launch install time separately.

If an intermediate state is visible, identify the Vite event sequence and choose a tested mitigation compatible with Epic 001's journal and recovery rules. A change in rename order alone is acceptable only if the browser test proves it removes the observed failure. Keep `node_modules` out of project copies; any dependency-cache change needs its own measured case and lockfile validation.

Done when findings and the chosen action are recorded, a repeatable manual runbook is checked in, and any implementation change passes the existing recovery tests plus a test for the observed failure.

### T7: Chat guidance and unsupported results (P1)

Keep the current preview-and-Apply flow for commands and structured answers, including revision/plan checks, Discard, conflicts and pending questions. Improve the empty chat with clickable example prompts drawn from one maintained list. Examples must be valid **in a stated project state**: basic commands can run on a fresh project; styling or sharing examples include their prerequisites and clarification steps. Chips fill the input rather than applying an edit without review.

Preserve the agent's optional UTF-8 diagnostic span and rejection reason in the API's `Unsupported` outcome; they are currently dropped by the server mapping. Use a valid span to identify the unrecognized prompt fragment, then show concise supported examples. A missing span uses the explanation alone. `NeedsClarification` continues to show its actual structured question and options, not a generic parser error. Do not claim a parser-accepted prompt will necessarily apply in every project state.

Done when API/server tests preserve diagnostic data, example tests verify parsing and required project-state outcomes, and GUI tests cover chips, unsupported text, questions and preview/Apply after launch and while stopped.

### T8: Automated integration and release gate (P1)

Add a server-level integration test that creates a project, launches the preview, sends a short scripted conversation through HTTP with explicit preview then Apply/answer steps, checks each structured outcome, and verifies that Vite serves the expected entry and transformed modules without errors. Do not assert generated page text in the HTTP route response: SPA fallback serves the entry HTML, while Solid renders page content in the browser. Use the T5 manual browser run to verify actual DOM, navigation and HMR; add headless browser automation only if a stable harness is available during implementation.

The automated test must stop and reap Vite even when an assertion fails, and must verify the process is gone. Run it locally and in the CI generated-build job with an explicit Node version and prerequisites; do not let missing dependencies turn it into a passing skip. Update the README or `docs/mvp.md` with runtime requirements, how to run server/GUI, the preview-and-Apply flow, supported examples, known limits and the T6 runbook.

Done when Rust tests, generated builds, the real preview test, the server integration test and the macOS manual GUI/browser run pass. Record local and CI results here when they actually occur.

## Delivery order

T1 establishes the contract; T2 supplies the preview lifecycle. T3 and T4 complete the first GUI launch loop, then T5 runs immediately so browser findings can inform T6. T7 may proceed after the wire contract and GUI controls settle. T8 closes the release gate. Keep fixes and their regression tests together. Update the status and investigation log as tasks finish.
